## 一、整体架构

### 1. 启动与镜像

沿用 P1 的字节级紧密镜像（任务书 P1 部分），P2 未改动这一层：

```
kernel.img = bootblock(512B, 唯一补零处) + 内核(字节) + AppInfo(448B)
apps.img   = 各 app 首尾相接
build/image = kernel.img + apps.img   （QEMU 用；上板时分别写 SD 卡）
```

- U-Boot 里 `loadbootd`（带 DASICS）/ `loadboot` 把第 0 扇区读进 0x50200000，
  bootblock 再把内核搬到 0x50201000，并经 `a0/a1/a2` 把
  「AppInfo 起始字节偏移 / 程序数 / apps 区起始字节偏移」交给内核
  （`head.S` 存进 `boot_*` 全局量，主线不再直接读 0x50200xxx）。
- `main()` 里 `init_task_info` 用**中转缓冲**读 AppInfo（块设备只能整扇区读、
  没有偏移参数，而 AppInfo 可能不在扇区边界上）。

### 2. 进程模型

- `pcb_t`（`include/os/sched.h`）：`kernel_sp / user_sp`（必须是前两个字段，
  偏移见 `asm/regs.h`）、就绪链表结点、pid、status、光标、`wakeup_time`，
  以及任务5 的进度统计字段（`wl_pos / wl_cols / has_wl`）。
- **每个任务一套内核栈 + 一套用户栈**（各 4K，从 `mm.c` 的分配器取；
  内核动态区 0x50500000 起、用户动态区 0x52500000 起）。
- 内核自己也有 PCB（`pid0_pcb`）：屏幕光标与调度都经由 `current_running`；
  pid0 常驻就绪队列，在所有用户进程都阻塞时兜底（空转在 `main` 的 `wfi` 循环里）。
- `tp == current_running`：`current_running` 声明为 `register ... asm("tp")`，
  由编译器保证赋值即写 tp；陷阱帧里也保存/恢复 tp。

### 3. 调度

- **任务1–2（非抢占）**：`do_scheduler` 走时间片轮转——活着（RUNNING）的排回队尾，
  取队首上场；被阻塞的由 `do_block` 自己摘走。
- **任务3（真系统调用后）**：触发点变成 `sys_yield` 与 pid0 空转循环。
- **任务4（抢占）**：时钟中断 `handle_irq_timer → do_scheduler`；内核空转用 `wfi`。
- **任务5（自适应）**：内核数出每架飞机"飞了多少格"，每次调度让**飞得最少的那架先飞**
  （时间片统一为 1/4 个时钟节拍），详见 `P2-design-review.md` C1。

### 4. 陷阱与系统调用

```
用户 ecall ──► stvec(Direct) ──► exception_handler_entry
   SAVE_CONTEXT：用 sscratch 换出内核栈顶，把 32 个 GPR + 4 个 CSR(288B) 压成陷阱帧
   tail interrupt_helper（ra 预置为 ret_from_exception）
      scause 最高位=1 → irq_table[中断号]；=0 → exc_table[例外号]
      exc_table[8] = handle_syscall：sepc += 4、syscall[a7](a0..a4)、结果写回 a0
   ret_from_exception → RESTORE_CONTEXT → sret
```

- 跳转表（任务1/2 用）与系统调用表（任务3 起）在 `init_jmptab / init_syscall` 里挂载。
- `sscratch` 的语义：**本任务的内核栈顶**（每次 `sret` 前由 `RESTORE_CONTEXT` 写好）。
- 内核态全程不重开 `sstatus.SIE`，避免内核被再次打断时把陷阱帧写到用户栈上。

### 5. 锁

- `spin_lock_t` + `mutex_lock_t{lock, block_queue, key}`，`mlocks[16]`。
- 同 key 必得同 handle（handle 即 `mlocks` 下标）。
- `do_mutex_lock_acquire`：**先入队再抢锁**（消除"检查锁状态"与"入队"之间的丢唤醒
  窗口），抢到就自我摘除，没抢到就睡；临界区用 `irq_save/irq_restore` 关中断。
- `do_mutex_lock_release`：置 UNLOCKED + 唤醒队首（两件事在同一段关中断里完成）。

## 三、修复过的关键问题（含定位过程）

### 抢占模式下"先被选中的任务稳定快 20%" —— 已修复

**现象**：时钟中断驱动、测试程序全部注释掉 `sys_yield` 时，两个**完全相同**的
测试程序产出稳定差 17~21%（print1/print2），且总是"先被选中的那个快"：交换选择
顺序后，快的仍然是先选中的那个（跟 pid 走、不跟程序走）。

**定位过程**（每一步都做了对照实验）：

| 步 | 实验 | 结果 | 排除/结论 |
|---|---|---|---|
| ① | 关掉 `sys_reflush` | 偏差照旧 | 与刷屏输出无关 |
| ② | 数被调度次数 / CPU 时间占比 / 片长 | 185/185/184、35.9%/36.7%、188k/200k | **不是"少给时间"** |
| ③ | 逐事件计数（每完成一次迭代，各任务让内核干了多少活） | 刷屏 1.000 次、吐格 1.12 个、putchar 1.12 次、putstr 20.8 字符 —— 两边一样 | 每格活相同，问题必在"时间"上 |
| ④ | 让**同一个程序跑两份**（同代码同窗口，只有 PCB/栈/队列位置不同） | 偏差仍 26.7% | 纯粹是"位置效应" |
| ⑤ | 把 `main` 空闲里的 `wfi` 换成忙等 | 偏差掉到 **-2.8%** | `wfi` 是主要放大器 |
| ⑥ | 加 `-icount`（虚拟时钟 = 指令数） | **Δ0.006%**（未修复代码也 Δ≤0.2%） | 根因是"墙钟时间基准" |

**机制**（原表述经队友独立复核后修正）：guest 的 rdtime 是**宿主墙钟**、不是执行量，
而 QEMU 在"1 核 + 高负载"的宿主上会被反复抢占 —— "墙钟走了、guest 没执行"的误差
客观存在。之所以会**按槽位稳定偏向**而不是随机抵消：`wfi` 是 guest 里唯一主动把宿主
CPU 让出去的地方，一睡一醒会把宿主调度器的相位与 guest 的轮转**对齐**（唤醒往往拿到
一个新鲜的时间片），于是等长墙钟窗口里"真正执行了多少"就按槽位系统性不均。
（注意：那段"白流的时间"记在 **pid0 自己**的时间片上——期限是在每个任务被换上时才
`bios_set_timer(get_ticks()+SLICE_LEN)` 的，不会混进后面任务的时间片。）

**决定性证据**：加 `-icount shift=3,sleep=off`（虚拟时钟 = 指令数，宿主负载影响不了
ticks↔工作量的换算）后，**同一份未修复的代码**偏差直接消失（队友实测 3202/3196、
4617/4618，Δ≤0.2%）；我在修复后的代码上复跑同样干净（34570 vs 34568，Δ0.006%）。
⇒ 缺的条件是"墙钟时间基准"，`wfi` 只是把误差从随机变成按槽位稳定。准确说法是
**"QEMU 时间基准 + 宿主超载"**，不要叫它"wfi 的 bug"。

**修复**：pid0（内核空转）退出轮转，只在"就绪队列为空"时上场兜底（时间片同大家
一样是 1/4 节拍）；`wfi` 只保留在怠速路径上 —— 同时去掉了"锚"和"浪费"。

> **勘误**：此前 commit message 里写"产出量提升约 3 倍"是错的（拿不同宿主负载下的
> 数据对比了）。两任务的产出**总量基本不变**（旧 6624+5284=11908 vs 新
> 5726+6028=11754），变化的是**分配**：原来 1/3 的时间片被怠速白占，现在还给用户
> 进程，理论上限 1.5×（队友在受控对照下实测 1.30×）。

**效果**：print1/print2 从 17~21% 降到 **0.4~5%**（多次实测 7004/7035、5143/5189、
5726/6028）；五机同速：总差 **0.04~0.1%**、累计进度锁步（互差 ≤5 格；另有 ~0.14%/位的顺序梯度，两次构建逐位重合，见 §四.6）。

**残余**：把 `wfi` 换成忙等（保留"pid0 参与轮转"的旧结构）单独测，偏差落在
-2.8% / +2.7% / +5.0% —— 说明 `wfi` 是主因，但还剩几个百分点随宿主负载起伏，
没有定位到独立机制，验收时按噪声看。

## 四、已知限制与说明

1. **时钟递送有抖动（QEMU + 宿主环境所致）**：实测抢占时刻相对 deadline 会晚
   几万 ticks，且随宿主负载变化（本机 1 核，负载高时更明显）。这是"guest 的
   rdtime 走宿主墙钟、而 guest 会被宿主挂起"的固有现象，不是调度逻辑的问题；
   上板（真机）不会有宿主争抢，但也没有验证过。
2. **测量环境**：本项目全部验证在 1 核宿主上跑，宿主负载会显著影响 tick 级
   测量（负载高时同样两个任务的产出差能从 1% 飘到 5%）。做对照实验时必须
   记录 `cat /proc/loadavg`，否则结论不可靠 —— 我踩过这个坑。
3. **Makefile**：app 加载窗口已改成按名字确定（不再依赖构建顺序），但改动
   app 数量后仍建议 `make clean && make all`。
4. **未上板验证**：本机无开发板，全部验证在 QEMU 完成；上板步骤见 P2 环境手册
   （`make floppy` + `minicom`），代码路径与 QEMU 完全一致（同一份 `build/image`）。
5. **任务5 的时间片统一为 1/4 个时钟节拍**（`SLICE_LEN = TIMER_INTERVAL/4` ≈ 3.75ms）：
   `do_scheduler` 把下一次时钟中断定在 `now + SLICE_LEN`；"同速"靠挑选顺序（谁飞得
   少谁先飞）实现，不靠改时间片大小。取 1/4 节拍是为了让每架每次上场只前进两三格，
   编队看着更连续；实测五机锁步，视觉上无卡顿。
6. **任务5 的算法迭代过三代，最终落在最简形式**：
   ① v1"时间片 ∝ 每格 CPU 成本"（前馈估计）：能对齐长期平均，但**没有反馈闭环**。
   用逐格位置轨迹实测 54 秒：五机累计进度**漂移出 302 格**（fly1 一整轮才 10 格）、
   任意 1 秒窗口速率差 10~42% —— 肉眼就是"速度明显不一样"。
   ② v2 在 v1 上叠"实测速度闭环"：连踩三个坑（矫正被前馈重算冲掉 / 积分饱和 /
   矫正系数全贴下限），放弃。
   ③ v3（现状）**"谁飞得少谁先飞"**（pick-min，等价于 stride/CFS 的虚拟时间调度）：
   内核只数每架飞过的格数 `wl_cols`，每次调度挑最少的先上场，落后的一架随后自动
   被补回来。护栏：凭落后插队有"配额"（选中一次 +1、前进一格清零、用尽退回普通
   轮转）——既防"上报位置永远不变"的程序霸占 CPU，又让"每格要烧好几片"的慢机
   拿到足额补偿（详见 design review C1）。
   实测：总差 **0.04~0.1%**、累计进度互差 **≤5 格**、1 秒窗口速率差
   中位 **3.7% / 最大 8.3%**；另一路独立复现（回归口径）另发现 **~0.14%/位的顺序
   梯度**（fly1 最快、fly5 最慢，pick-min 版与配额版两次逐位重合；机制未验证、
   肉眼不可辨）。而且把 v1/v2 的成本估计、时间片重算整层都删掉了 —— 代码更简单。
   > 迭代中踩过的坑保留在 `wl_cols` 的补记里："每轮回卷少算 1 格"（fly 先报当前列
   > 再飞这一列，回卷那一格会被漏统计）——不补的话短轮任务被系统性少算（fly1 每轮
   > 少 10%），"谁快谁慢"的排序会被带偏。

> **口径澄清**（答辩容易被追问）：同速的判据是**累计进度锁步**（五架飞过的总格数
> 始终咬在一起，差不超过几个格子），不是某一次瞬时位置或某一秒的采样——宿主噪声会
> 让单次采样起伏，但锁步是构造性的（落后必被优先补上）。

7. **验收辅助**：跑测试时按 **Ctrl+C** 可让内核热重启，一秒回到选任务提示符
   （测试程序是死循环、调度期间内核不读键盘，没有别的停法）。正常验收不会按到
   它；不想要的话删掉 `kernel/irq/irq.c` 里 `handle_irq_timer` 开头那三行即可。
