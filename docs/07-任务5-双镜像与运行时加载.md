> AppInfo 相对扇区、`list` 信息命令。任务书原文引用一律以

## 1. 全景

```
createimage（Task 5 形态：双镜像）
   │ kernel.img = bootblock(1) + 内核(K) + AppInfo(A=1)      ==> (1+K+A)×512 字节
   │ apps.img   = 各 app 紧凑（start_sector 记录 apps.img 内相对扇区）
   │ 0x1f8/0x1fc/0x1fe 仍写在 kernel.img 第 0 扇区
   ▼
Makefile：cat kernel.img apps.img > image   ← 等价于两文件写入 SD 卡连续扇区
   ▼ QEMU 挂载单块磁盘 build/image
bootblock：读内核(1..K) → a0=1+K / a1=app数 / a2=1+K+A(apps基址) → jal kernel
   ▼ head.S 存 a0/a1/a2 → main → init_task_info（读 AppInfo 扇区 1+K，仍 512B 缓冲）
   ▼ 按名：
load_task_img：匹配 tasks[i].name
   → bios_sd_read(vaddr_entry, sector_num, boot_apps_base + tasks[i].start_sector)
   → 只读目标 app（要点 4），别的 app 一个字节都不读
list 命令：show_task_list() 打印 name/start(rel)/size/entry
```

## 2. 双镜像制品与"cat 拼接 == 连续扇区写入"的等价性

```
kernel.img = bootblock(1) + 内核(K) + AppInfo(A=1)
apps.img   = 各 app 紧凑（不带头部信息）
build/image = kernel.img ∥ apps.img（Makefile 的 cat；createimage 绝不直接写 image）
```

等价性论证（要能讲清楚）：
1. `build/image` 物理上只是一串连续字节，BIOS 按扇区号寻址、**没有文件边界概念**；
2. QEMU 侧只有一块盘（`-drive file=build/image`），所以"两个镜像"只能拼回一文件
   ——"把两个文件分别写入 SD 卡连续扇区"在文件层面就是 `cat`；
3. 板卡侧真要两文件分写时，offset = `1+K+A` 扇区（Makefile floppy 方案 B 注释里
   有计算式；默认方案 A 是单 dd 写 image）。

> **为什么 AppInfo 必须在 kernel.img**：内核启动 `init_task_info()` 要读 AppInfo；
> 若它在 apps.img，启动阶段就得读应用区 → 违反任务书"只把内核镜像从SD卡读取到
> 内存中"与 slide 25"only the kernel image is loaded"。这是布局的必然性，不是选择。

## 3. bootblock 传三参（a0 / a1 / a2）

```asm
read_done:
	move  a0, t0              // a0 = 1 + K（AppInfo 起始扇区）
	li    t3, os_size_loc - 4
	lh    a1, 0(t3)           // a1 = app 数
	addi  a2, t0, 1           // a2 = 1 + K + A（A=1，apps 基址 = kernel.img 总扇区数）
	jal   kernel
```

head.S 在清完 BSS 后把三值存进 `boot_appinfo_sector/boot_appnum/boot_apps_base`。

## 4. AppInfo 的 start_sector = apps.img 内相对扇区号

- **语义**：`tasks[i].start_sector` 是"在 apps.img 里的第几个扇区"，不是 SD 绝对扇区。
- **原文背书**：要点 3"在内核镜像中标识**用户镜像文件中**各个用户程序的地址、大小"，
  就是相对 apps.img 的局部语义。
- **为什么相对更好**：两项镜像真正解耦——AppInfo 与 kernel.img 长度 K、拼接顺序无关；
  加载时 `bios_sd_read(vaddr, num, boot_apps_base + rel)`，base 只有 bootblock 一处取值。
  若存绝对扇区，K 一变所有槽位全错。
- **base 两方可自算**：`apps 基址 = 1+K+A`；bootblock 从 0x1fc 拿 K、+1、+A 即得。

## 5. loader：只加载要运行的用户程序（要点 4）

```c
if (strcmp(tasks[i].name, taskname) == 0)
{
    if (bios_sd_read(tasks[i].vaddr_entry, tasks[i].sector_num,
                     (unsigned)(boot_apps_base + tasks[i].start_sector)) != 0)
        return 0;
    return (uint64_t)tasks[i].vaddr_entry;
}
```

`bios_sd_read` 的第三参现在是 `base + rel`：只有名字匹配到了，才去读 apps区 对应区间。
启动阶段（bootblock 1..K + init_task_info 读 1+K）**完全不触碰** apps 区。

## 6. list 命令（slide 25 可选项）

```c
if (strcmp(name, "list") == 0) { show_task_list(); continue; }
```

```c
static void show_task_list(void)
{
    bios_putstr("name              start size   entry\r\n");
    for (int i = 0; i < task_num; ++i)
    {
        /* pad 到 16 列对齐；put_uint 十进制；put_hex 十六进制（内核无 itoa，自写） */
        bios_putstr(tasks[i].name);
        put_uint(tasks[i].start_sector);       /* 相对扇区 */
        put_uint(tasks[i].sector_num);
        put_hex(tasks[i].vaddr_entry);
        bios_putstr("\r\n");
    }
}
```

真实输出（`.scratch/task5-qemu.log`）：

```
name              start size   entry
2048            0    10    0x52000000
auipc           10    2    0x52010000
bss             12    1    0x52020000
data            13    9    0x52030000
```

## 7. 验证与验收（Task 5）

注入：`list → auipc → bss → data → 2048 → 回车 → q → nope → 空行`。
断言三大块：
1. **制品**：kernel.img 大小 == (1+K+A)×512；apps.img == Σ(app×512)；`image == 两者和`；
   hexdump 关键点（标志串、0x1f8/0x1fc/0x1fe、AppInfo 槽位）与 createimage 打印一致；
2. **行为回归**：4 个 app 按名启动、未知名拒绝、空行 invalid、bss 检查通过；
3. **list**：表头 + 4 行 entry，且 rel start 与 AppInfo 字节一致（如 auipc rel=10）。
   启动阶段"只读 kernel.img"以**代码路径审查级 + 日志证据**两层论证（09 会展开局限）。

## 8. 收官护栏

`include/os/task.h` 末尾有三条 `_Static_assert`：

```c
_Static_assert(sizeof(task_info_t) == 28, "...");
_Static_assert(TASK_NAME_LEN == 16, "...");
_Static_assert(TASK_MAXNUM * sizeof(task_info_t) <= SECTOR_SIZE, "... AppInfo 1 扇区前提");
```

它们把"bootblock 硬编码 A=1"、createimage 与内核结构体一致等**前提**绑到编译期：
任何一项被破坏，构建直接失败，而不是运行期跑飞。（注意：Makefile 不跟踪头文件依赖，
改了 task.h 记得 `make clean && make elf`。）
